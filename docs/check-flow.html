The review pipeline

architecture · src/pipeline.js

A review is a single call to runPipeline() (src/pipeline.js), the tool's core: it performs an analysis of the provided add-on and returns a Review - the findings and manual-review notes. The call loads and resolves the add-on, builds the run context, then hands off to the orchestrator, which runs the checks. Everything below happens inside it.

Setup

Nothing is checked until the add-on is loaded, classified, resolved and parsed - the pipeline's first job, and it does every expensive thing exactly once. The amber boxes are the ones that matter: they resolve the review state - invalidExperiment, the mode (plus the advisory scaNotRequired) and the review target - and everything after them, every check, keys off those. After Phase 4, Phase 5 runs the review (a single runChecks() call, detailed in The orchestrator) then finalizes the Review for the report.

The built XPI is analysed first, and always. Phase 2 runs the full XPI analysis - vendor, classify, identify, parse - before the mode is known, yielding xpiAddon.bundled and the XPI's parsed sources; Phase 4 then projects those into the shipped ctx (siblings.xpi) that every input: xpi check reads. Because the XPI is analysed the same way in both modes, an input: xpi check sees the identical artifact whether the run is SCA or XPI - the reason for the rework. There is no separate “light” classification pass any more: the XPI-only advice reads that same xpiAddon.bundled. That advice is all it is - --sca-root alone decides the mode, and an SCA submission is always reviewed as SCA. resolveXpiOnlyAdvice() only asks whether the developer could have skipped the archive: is the shipped code readable, does the archive carry no transpiled source kind, and is every shipped script byte-identical to one in the archive? All three yes and sca-not-required (info) says so for next time. Routing on that answer is what the tool used to do, and it was a bypass: a committed, unminified dist/ inside --sca-source is its own twin under any content test. In SCA the readable source is then analysed on its own in Phase 3 (siblings.source); in an XPI review there is no second artifact, so siblings.source simply aliases the shipped ctx. An invalid Experiment skips the analysis entirely (it reads no code), and is the one thing that still pins an --sca-root run to mode = xpi.

The invalid-Experiment path is not an early exit - it runs on to the orchestrator, which reviews the shipped XPI with the single reject check. It only skips work, in one step: setting invalidExperiment pins the mode and bypasses everything after it - the library hashes, the classification, the vendor block, the parse. Not one line of the add-on's code is read, so ctx.jsSources is empty; the reject check judges from the manifest, the experiment classification and the schema - which is resolved before the decision because the check resolves API paths through it.

The stores

What setup leaves behind is a set of shared stores. The diagram reads left to right in four columns: the producer step, the store it builds, the access layer, and the checks. A store (solid) is raw and eager - built once during setup (ctx.schema, addon.vendor/bundled, the per-source src.extracted.* fields), whether or not anything reads it. A cache (dashed) is a derived, lazy view - apiResolution, permissionAnalysis, outboundSinks, evalScan, locales, and the reachability graph - computed from stores on the first read that needs it, then memoized (so a cache nobody reads is never built). The lazy caches never re-parse: they derive from the precomputed src.extracted stores (a check reading before the extraction pass ran throws "a check is a pure reader, it never parses"). The small unlabeled circles are relays - pure layout, so a store a check reads directly still lines up in the last column. Solid arrows are "produces / derives from"; dashed are "read by".

A check is a pure reader. It never parses, never fetches, never mutates. So two checks asking the same question always agree, and peak memory stays at a single AST, regardless of how much code the add-on ships.
store built by what it holds
addon.vendor resolveVendor() → verifyVendor() The declared third-party libraries, resolved to their sources and verified over the network, plus the vulnerability audit. The vendor checks are pure readers of it.
addon.bundled classifyFiles() → assembleBundled(), finalized by identifyBundledLibraries() The per-file classification (authored / library / minified / obfuscated / vendored) and the nonAuthored skip set that every content scanner honours. identifyBundledLibraries() (the CDN + not-popular-vendor reconciliation) finalizes the split - it both adds and removes - which is why the parse runs after it.
src.extracted
(per ctx.jsSources entry) 		runExtractionPass() Each source is parsed once; the small per-file results (API usage, loader refs, network sinks, remote-code refs, the comment-free code atoms …) are stored and the AST is dropped. This is why no check ever re-parses.
ctx.schema resolveReviewSchema() The SchemaIndex for the selected channel, with any Experiment namespaces registered into it, plus the local annotation overlay.
the lazy ctx caches memoized on first read permissionAnalysis, apiResolution, evalScan, outboundSinks, locales … - derived on demand by whichever check asks first from the precomputed stores (no re-parse), then shared with the rest.

Which stores a check may reach is not open either. Every check declares an input, and routeCtx - the single place routing is decided, shared by the main loop and the deferred loop so they can never drift - hands it the sibling ctx for that input. Routing is total: source is a first-class sibling like the rest, there is no default artifact to fall through to, and a declared input with no sibling (a stray input: build in an XPI review) throws rather than silently running on the wrong corpus. A check reads exactly one artifact and cannot reach another's. What the input resolves to depends on the review mode:

input SCA review (readable source + built XPI) XPI review (one artifact)
source the readable source (siblings.source) the built add-on (siblings.source)
xpi the built XPI (siblings.xpi) the built add-on (siblings.xpi)
build the SCA build files (siblings.build) — (SCA-only)
manifest the shipped manifest (no file corpus) the shipped manifest

In an XPI review there is one artifact, so siblings.source and siblings.xpi are the same ctx. Every check declares an input, and that is both the ctx it runs on and the artifact its output is labelled as - ctxForRule recovers the latter for the report’s [XPI]/[SCA] labels and the folder-collapse, once findings come back as a flat list carrying only a rule id.

The orchestrator

With the stores in place runChecks() takes over. A check's phase is simply the registry.yaml section it lives in - never declared on the entry, so the two cannot disagree. The orchestrator looks up the phases it wants, in the order it runs them, which makes any section it never asks for inert.

phase (= section) when it runs run by example check
invalid-experiment-phase ONLY when the add-on is an invalid Experiment (ctx.invalidExperiment) - and then it is the only phase that runs at all: the whole rest of the review is skipped. runChecks experiment-not-allowed
deterministic-phase Every check of a normal review. runChecks missing-permission

runChecks() (src/checks/registry.js) runs the whole review: the phase's checks in its main loop, then the unused-folder collapse. It returns the finished findings, manual items and the checks that ran; runPipeline()’s Phase 5 (src/pipeline.js) just calls it and assembles the Review. Every check goes through the same per-check runner, runOneCheck(). The phase runner is runChecks()’ main loop (src/checks/registry.js): it walks a phase’s gated checks in order, routes each to its input’s ctx (routeCtx), runs it through runOneCheck(), and collects the results - findings onto the returned list, escalations onto the manual-review list. runOneCheck() decides what to do with a check purely from the shape its run() returned - never its phase; a check that throws becomes a single check-failed finding so the rest still run; and only the orchestrator routes anything to manual review. This loop is also where the lazy caches are computed - the first check to read one builds it inside its run() and memoizes it on ctx.addon for every later check (see The stores).

Escalating what the code cannot settle

A check that cannot settle a case does not guess: it escalates, and the reviewer is handed the concrete file:line to look at. The escalation says which of the two review buckets it belongs to.

Most are questions about the add-on’s own code, and land under Extended Code Review. Some cannot be answered by reading the package at all - what the ATN listing discloses about a privacy policy or a native application, or whether the build really produces the shipped XPI, which only reproducing it settles. A remote font @import inside a stylesheet whose content matches a published file of a known library release is the same kind of case: the line is that release’s, not something the developer wrote, so what is left is whether shipping it as published is acceptable here - a judgement a person owns. That is a different question from “is this even remote?”, so it is a different check - vendored-remote-resources, which declares escalation: manual-review and shares one scan with remote-resources. Which section a check’s cases land in is declared on the check, never per case.

Either way the entry carries its suggested response: once the reviewer settles the case against the add-on, that is the text the developer receives.

The permission scan shows what an escalation carries. The unused-permission check does not just decide whether a permission’s usage tokens are present - it records where each occurs, so the reviewer reads concrete lines rather than answering a bare yes/no over the whole add-on. A permission whose tokens appear nowhere at all is decided in code, as a warning finding.
