The review pipeline

architecture · src/pipeline.js

A review is a single call to runPipeline() (src/pipeline.js), the tool's core: it performs an analysis of the provided add-on and returns a Review - the findings and manual-review notes. The call loads and resolves the add-on, builds the run context, then hands off to the orchestrator, which runs the checks. Everything below happens inside it.

Setup

Setup does only what every review needs before any check can run: it loads the add-on, resolves the schema, and - for an Experiment - decides the Experiment verdict and registers the Experiment's APIs. The amber boxes are the ones that matter: they resolve the review state - invalidExperiment, the submitted source archive and the review target - and every check keys off those. The mode is not one of them: it is DERIVED from --sca-root and the Experiment verdict, so it cannot disagree with the steps that ran. These eager steps are declared in SETUP_STEPS and walked by one loop, which is also where the Setup feed's [n/total] comes from.

Everything else the review knows about an artifact - its vendor reading and audits, the classification of its bundled code, the CDN identification, its parsed sources, the build trace - is computed when a check first asks for it, through an async getter on the check's ctx (ctx.vendor(), ctx.bundled(), ctx.jsSources(), ctx.apiUsages(), ctx.buildReview(), ctx.lockInstalls(), src/review/products.js). A getter computes once per artifact and answers every later check from the same result, and it answers only final data: the stages behind it run in their fixed order, and the ones that revise an earlier answer (the CDN identification, the audits) finish before it is handed over. A review computes what its checks read and nothing more - a rejected Experiment, which stops at a first check that reads none of it, computes none of it. Each stage prints its line in the Activity feed, under the check that first needed it.

Before anything is read, the review claims its work folder (<name>-<timestamp>/ beside the add-on): created if missing, and every name this run will create there checked to be free, so nothing in it is overwritten. A start that fails before the review exists gives those names back. Loading is then where the submission becomes the review's own copy. A .xpi is extracted to xpi/ in the work folder, and a submission handed over as a folder is walked first (so every refusal fires before anything is written) and copied there; either way the copy is read back through the same directory walk. That folder is XPI_ROOT, the one place the package is read from: by the checks below, by a reviewer, and by an agent under --llm-review.

The built XPI is analysed the same way in both modes. Its getters run the full XPI analysis - vendor (in an XPI review), classify, identify, parse - whenever a check routed to it asks, so an input: xpi check sees the identical artifact whether the run is SCA or XPI. --sca-root alone decides the mode, and a source submission is always reviewed as one. Whether it is SHAPED like one is a separate question, asked by two checks rather than by setup, both on input: all - the one route that can carry more than one artifact, and which each of them leaves early without an archive: sca-xpi-declares-vendoring warns when the XPI carries vendoring information that belongs in the archive, naming the files, and sca-xpi-fully-included-in-archive warns when every file the XPI ships is already in the archive. Routing on either answer would be a bypass: a committed, unminified dist/ in the archive is its own twin under any content test, so a build could be dressed up as source and shrink its own review. In SCA the readable source has getters of its own (siblings.source); in an XPI review there is no second artifact, so siblings.source simply aliases the shipped ctx. An invalid Experiment is the one thing that still makes an --sca-root run an XPI review.

The invalid-Experiment path runs on to the orchestrator like any other review. Setting invalidExperiment pins the mode and leaves the source archive unread. The first check, experiment-not-allowed, judges from the manifest, the experiment classification and the schema - which is resolved before the decision because the check resolves API paths through it - and its error aborts the review, so no other check runs and not one line of the add-on's code is read.

The stores

What the checks read is a set of shared stores. The diagram reads left to right in four columns: the producer step, the store it builds, the access layer, and the checks. A store (solid) is raw - ctx.schema, built once in setup, and the artifact data behind the getters (ctx.vendor(), ctx.bundled(), the per-source src.extracted.* fields of ctx.jsSources()), each built once, the first time a check asks for it. A cache (dashed) is a derived, lazy view - apiResolution, permissionAnalysis, outboundSinks, evalScan, localeMessages, and the reachability graph - computed from stores on the first read that needs it, then memoized (so a cache nobody reads is never built). The lazy caches never re-parse: they derive from the precomputed src.extracted stores (a check reading before the extraction pass ran throws "a check is a pure reader, it never parses"). The small unlabeled circles are relays - pure layout, so a store a check reads directly still lines up in the last column. Solid arrows are "produces / derives from"; dashed are "read by".

A check is a pure reader. It never parses, never fetches, never mutates. So two checks asking the same question always agree, and peak memory stays at a single AST, regardless of how much code the add-on ships.
store built by what it holds
ctx.vendor() resolveVendor() → verifyVendor() The declared third-party libraries, resolved to their sources and verified over the network, plus the vulnerability audit - computed on the first ask, on the review target only. The vendor checks are pure readers of it.
ctx.bundled() classifyFiles() → assembleBundled(), finalized by applyUnverifiedVendor() and resolveCdnLibraries() The per-file classification (authored / library / minified / obfuscated / vendored) and the nonAuthored skip set that every content scanner honours. The CDN + not-popular-vendor reconciliation finalizes the split - it both adds and removes - which is why the parse runs after it.
src.extracted
(per ctx.jsSources() entry) 		runExtractionPass() Each source is parsed once; the small per-file results (API usage, loader refs, network sinks, remote-code refs, the comment-free code atoms …) are stored and the AST is dropped. This is why no check ever re-parses.
ctx.schema resolveReviewSchema() The SchemaIndex for the selected channel, with any Experiment namespaces registered into it, plus the local annotation overlay.
the lazy ctx caches memoized on first read permissionAnalysis, apiResolution, evalScan, outboundSinks, locales … - derived on demand by whichever check asks first from the precomputed stores (no re-parse), then shared with the rest.

Which stores a check may reach is not open either. Every check declares an input, and routeCtx - the single place routing is decided, shared by the main loop and the deferred loop so they can never drift - hands it the sibling ctx for that input. Routing is total: source is a first-class sibling like the rest, there is no default artifact to fall through to, and a declared input with no sibling (a stray input: sca in an XPI review) throws rather than silently running on the wrong one. A check reads at most the one artifact its route names, and cannot reach another's. (A by-hand manual-checks entry runs nothing and reads no artifact, so it declares input: none, which is not one of these routes and has no sibling. A handful of checks that do run also read no artifact - only the shared records, ctx.manifest and ctx.experiments - and declare xpi, because both of those are the built XPI's.) What the input resolves to depends on the review mode:

input SCA review (readable source + built XPI) XPI review (one artifact)
source the submitted archive — siblings.source is a POINTER at whichever artifact is the review target, so here it is the very same ctx as siblings.sca the built add-on — the same ctx as siblings.xpi
xpi the built XPI (siblings.xpi) the built add-on (siblings.xpi)
sca the submitted source archive (siblings.sca) — (SCA-only)
all BOTH, as ctx.xpi + ctx.sca and no ctx.artifact (siblings.all) - the only route that can see more than one the built add-on as ctx.xpi, with ctx.sca null - the route says what the review holds, so a check on it tests before it reads

An input says what a check READS. What its findings are ABOUT is answered separately, by whatever holds the file: each Addon carries its own kind and mints loci with at, the shipped manifest.json record does the same with locus, and every finding, escalated case and feed note carries one that a holder minted. Nothing fills it in afterwards — assertLocus refuses a locus that cannot say which artifact it is in. ctxForRule recovers the sibling a check ran on, for the folder-collapse and for recording which artifact a swept case will be in; both need the artifact itself rather than a label.

The orchestrator

With the stores in place runChecks() takes over. A check's phase is simply the registry.yaml section it lives in - never declared on the entry, so the two cannot disagree. The orchestrator looks up the one phase it runs, which makes any section it never asks for inert.

phase (= section) when it runs run by example check
deterministic-phase Every check, in order, until one aborts the review. The first is experiment-not-allowed, which stops a rejected Experiment before any other check runs. runChecks missing-permission

The phase runner is runChecks()’ main loop (src/checks/registry.js): it walks a phase’s gated checks in order, routes each to its input’s ctx (routeCtx), runs it through runOneCheck(), and collects the results - findings onto the returned list, escalations onto the manual-review list. runOneCheck() decides what to do with a check purely from the shape its run() returned - never its phase; a check that throws becomes a single check-failed finding so the rest still run; and only the orchestrator routes anything to manual review. A check whose error aborts the review (abortsReview: it names a review-early-exit reason) is the last one the loop runs: no check after it runs, and nothing it would have read is computed. This loop is also where the lazy caches are computed - the first check to read one builds it inside its run() and memoizes it for every later check (see The stores).

Escalating what the code cannot settle

A check that cannot settle a case does not guess: it escalates, and the reviewer is handed the concrete file:line to look at. Which of the two review buckets it belongs to follows from who the check wrote its question for.

Most are questions about the add-on’s own code, and land under Extended Code Review. Some cannot be answered by reading the package at all - what the ATN listing discloses about a privacy policy or a native application, or whether the build really produces the shipped XPI, which only reproducing it settles. An add-on name written straight into the manifest is another: the trademark policy allows “<name> for Thunderbird”, and recognising that form needs the name’s language, which an unlocalized name never states - so trademark-thunderbird-name asks a person, while its sibling, whose names arrive tagged with their locale, asks an agent. A remote font @import inside a stylesheet whose content matches a published file of a known library release is the same kind of case: the line is that release’s, not something the developer wrote, so what is left is whether shipping it as published is acceptable here - a judgement a person owns. That is a different question from “is this even remote?”, so it is a different check - vendored-remote-resources, which authors only an instructions-for-human and shares one scan with remote-resources. A check that authors wording an agent can be handed is screened and lands under Extended Code Review; one that authors only the human half lands under Extended Manual Review. Which section a check’s cases land in follows from the check, never from the case.

Either way the entry carries its suggested response: once the reviewer settles the case against the add-on, that is the text the developer receives.

The permission scan shows what an escalation carries. The unused-permission check does not just decide whether a permission’s usage tokens are present - it records where each occurs, so the reviewer reads concrete lines rather than answering a bare yes/no over the whole add-on. A permission whose tokens appear nowhere at all is decided in code, as a warning finding.
