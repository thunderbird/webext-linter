Build modifies code error

build-modifies-code

What it detects

This check scans nothing. In a source review the reviewer reads the archive, and the build turns it into the add-on. A build step that changes the content of a file on its way into the add-on, a file from the archive or from a dependency, ships a file nobody read: a patch applied to a dependency, a piece appended to or cut out of a file, or a value substituted into it. A byte comparison of the shipped files cannot find such a change reliably, since a step that also bundles or minifies defeats it. The change itself sits in the archive, in a build script, a patch file or a bundler config, so what this check contributes is a blind spot: a standing brief naming what to look for there.

Every source review that is not aborted prints that brief under Standard Code Review, for a reviewer covering it by hand. When an agent is reviewing, it sweeps the archive for the same thing and hands back what it finds. Each location comes back as a case of this check:

  • A step that adds, removes or replaces anything in a file, a dependency's or the developer's own, comments included, is reported. What the change does, and why it was made, play no part.
  • A step that only substitutes a value into a file, such as a bundler define, an environment value or a version stamp, goes to the reviewer, who decides whether the add-on may ship it.
  • Selecting a file and adding it to the add-on as it is changes nothing. Neither do compiling, transpiling, bundling and minifying, which are what a build is for.

A file a VENDOR file declares is compared with its declared source by vendor-modified. This check is the same rule for code the build changes.

When it fires The developer is told that the build changes the content of a file on its way into the add-on, so the add-on ships code that differs from the source, and is asked to make the change in the source itself or remove it from the build.
