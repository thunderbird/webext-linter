Build modifies code error

build-modifies-code

What it detects

This check scans nothing. In a source review the reviewer reads the archive, and the build turns it into the add-on. Code a build step changes on its way into the add-on ships as something nobody read: a patch applied to a dependency, code appended to a file, or a code file the build writes itself. A byte comparison of the shipped files cannot find such a change reliably, since a step that also bundles or minifies defeats it. The change itself sits in the archive, in a build script, a patch file or a bundler config, so what this check contributes is a blind spot: a standing brief naming what to look for there.

Every source review that is not aborted prints that brief under Standard Code Review, for a reviewer covering it by hand. When an agent is reviewing, it sweeps the archive for the same thing and hands back what it finds. Each location comes back as a case of this check:

  • A third-party file, a dependency's or a vendored one, must reach the add-on exactly as it was published. Any change to it, comments included, is reported.
  • In the add-on's own files, code the build adds or changes is reported, and so is a code file the build writes itself. manifest.json counts as code here. What the change does, and why it was made, play no part.
  • No change: removing the add-on's own code for a build variant, filling in a placeholder in it (a bundler define, an environment value, a version stamp), adding a comment to it, a bundler choosing which file to include, writing a file that is not code, and compiling, transpiling, bundling and minifying, which are what a build is for.

A file a VENDOR file declares is compared with its declared source by vendor-modified. This check is the same rule for code the build changes.

When it fires The developer is told that the build changes code on its way into the add-on, so the add-on ships code that differs from the source, and what the build may and may not do to it.
