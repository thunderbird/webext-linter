Missing lock file for a ranged dependency error

xpi-lock-file-missing

What it detects

A dependency declared in a shipped package.json as a version RANGE, which no lock file resolves. Such a declaration says a bundled file was copied from a published release, and the review checks that literally by fetching that release and comparing it against the shipped bytes. A range names no single release, so the lock committed beside it is what says which one was bundled.

This is the requirement for an add-on submitted as a built XPI, where package.json serves to declare bundled third-party code. The vendoring guide asks a developer who keeps a range to commit the lock file alongside it - package-lock.json, npm-shrinkwrap.json or pnpm-lock.yaml - because the lock records the exact version that was bundled. With no lock at all, nothing resolves the range. A source-code submission answers the same question against the tree the reviewer installs, so this check does not run there. A lock that IS committed and still resolves nothing is a different remedy and a different check, xpi-lock-file-invalid; a dependency is never reported by both. Whether the source a dependency names is supported at all is a separate question, answered by Unsupported dependency source.

When it fires The developer is told the dependency is a range with no lock file to resolve it, and is asked to commit the lock their package manager wrote, or to pin the dependency to a bare version instead.

Source of truth: src/checks/rules/xpi-lock-file-missing.js and its entry in assets/registry.yaml.
