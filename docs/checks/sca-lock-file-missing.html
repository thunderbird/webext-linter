Missing lock file error

sca-lock-file-missing

What it detects

A source-code submission whose build installs dependencies but ships no lock file. Reviewers reproduce the build with the package manager's strict install, and that refuses to run without a lock file, so the submitted source cannot be shown to produce the submitted add-on.

Only the package.json at the root of the submission is read, because that is where the build starts, and one that cannot be read as a JSON object declares nothing this check can hold a lock file to. Whether it declares build scripts makes no difference: in a source submission a package.json is always a build manifest, and whatever it declares gets installed. Only an add-on submitted as a built XPI may use one to declare the published packages its bundled files came from, and a source archive declares those in its VENDOR file instead. The lock is owed by the manifest itself, not by what it happens to declare: both installers refuse to run without one whatever it holds, and a root that declares nothing of its own is a manifest whose declarations live elsewhere rather than a submission that installs nothing. npm and pnpm are the only supported package managers, so theirs are the only lock files that count, and a lock file's presence is decided by its name rather than by reading it - one that exists but cannot be read is reported as an invalid lock file instead.

A submission built with a package manager this review does not support is left alone here. A disallowed tool and a missing or unusable lock are one fact, so it is reported once, by the check whose subject the tool is - and that check stops the review just as this one would.

When it fires The add-on is told that its source includes no npm or pnpm lock file, that one is needed for a reproducible install, and that it should commit the lock file its package manager writes. The report then closes, saying it is incomplete because the build cannot be reproduced.
It stops the review This check is one of the few that settle the submission on their own. When it reports, nothing further is put to a reviewer: the report drops every to-do item they would have been asked, keeps the code-review sections, and the developer’s text ends on the reason it is incomplete (“A build that cannot be reproduced”). Every question that remains would depend on installing and building the add-on, which cannot succeed, so the work it would otherwise put to a reviewer cannot change the outcome.
