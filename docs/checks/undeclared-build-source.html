Build process review error

undeclared-build-source

What it detects

In a source-code submission the reviewer builds the add-on from the readable source, but the dependency audit only reads the root manifest and lock file. A build script or config could ignore the manifest and pull code or resources from an undeclared source, leaving the declared dependencies a clean decoy.

The build corpus is collected once, up front, by the build analysis, in the setup phase over the build-relevant files (collected by following the package manifest, so build output and tooling the build never runs are never sent). Nothing then says what that build does: reproducing it is the reviewer's attestation that the shipped XPI comes from the source they read, and no analysis substitutes for it. So this check emits no finding of its own and escalates EVERY source-code submission to Extended Manual Review — one whose source documents no build at all included, since the shipped bytes still have to be accounted for.

What the analysis contributes is detail the reviewer reads with it: the steps it could not statically follow (an opaque orchestrator, a network fetch in a script) are named in the escalation, and the entry anchors at the submission's own package.json where there is one. Under --llm-review a source-code review also spawns an agent that reports how to produce the release build for Thunderbird, so the reviewer has the steps in front of them — a report they work from, never a verdict on the build.

When it fires Every source-code submission is escalated to Extended Manual Review, where a reviewer reproduces the build by hand and confirms that it produces the shipped XPI and pulls only from the declared dependencies. Where they find it does not, the add-on is told that every part of the build must come only from the dependencies declared in the manifest and lock file.

Source of truth: src/checks/rules/undeclared-build-source.js (fed by the setup build analysis, src/build/analyze.js) and its entry in assets/registry.yaml.
