Unpinned vendored library error

xpi-package-unpinned

What it detects

A dependency declared in a shipped package.json that does not name one exact release. Such a declaration says a bundled file was copied from a published package, and the review checks that literally by fetching that release and comparing it against the shipped bytes. A range names no single release, so there is nothing to compare it with.

This is the requirement for an add-on submitted as a built XPI, where package.json serves to declare bundled third-party code. A source-code submission answers the same question with its lock file instead, so this check does not run there. No lock file is consulted here either: a lock is a build artifact that has no place inside a built add-on, and reading one found there would let a range stand in for an exact version on the word of a file nothing verifies. Whether the source a dependency names is supported at all is a separate question, answered by Unsupported dependency source.

Decision flow

flowchart TD

  C -- yes --> S2([skip: a question of source, not pinning])
  C -- no --> ERR([ERROR: unpinned vendored library])

When it fires The add-on is told the dependency is not pinned to an exact version, that only bare version values such as "4.17.21" are supported, and that each dependency in the package.json included in the XPI should be updated to that form.

Source of truth: src/checks/rules/xpi-package-unpinned.js and its entry in assets/registry.yaml.
