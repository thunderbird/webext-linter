The built XPI declares its own vendoring warning

sca-xpi-declares-vendoring

What it detects

A source-code submission whose built XPI carries vendoring information of its own: a VENDOR file, a package.json, or a lock file. In a source-code submission those belong in the archive — that is the copy the reviewer reads and the build installs from — not in the package you ship.

This does not re-route the review. A source archive is always reviewed as one, and this finding changes nothing about the review it appears in. Routing on it would be a bypass: a committed, unminified dist/ in the archive is its own twin under any content test, so a build could be dressed up as source and shrink its own review. At warning severity --warnings-as-errors can still refuse a submission at intake, while an update that got its packaging wrong is simply told what to change.

All three file kinds count, matched by name at any depth in the package, because a declaration is a declaration wherever the packaging put it. A shipped one means one of two things and the remedy differs: the submission type was misread, and the declarations belong in the archive; or an XPI-only submission was meant all along, and no archive was needed. The response offers both.

It names the files. Every match is a locus, and the response names none of them, so the findings collapse into one entry listing the offending paths once. Each is minted by ctx.xpi — the side those files are in. This check’s route carries two artifacts and so names neither, and asking the holder is how a finding says which one it means.

When it fires The built XPI ships at least one VENDOR file, package.json or lock file. The developer is asked to remove them from the XPI and declare the dependencies in the archive instead, or to submit just the XPI if it needs no archive behind it. This review itself is unaffected: it is a full source review either way.

Source of truth: src/checks/rules/sca-xpi-declares-vendoring.js (which reads only the XPI, of the two artifacts its input: both route carries) and its entry in assets/registry.yaml.
