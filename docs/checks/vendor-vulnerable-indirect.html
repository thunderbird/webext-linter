Vulnerable indirect dependency error

vendor-vulnerable-indirect

What it detects

A package the add-on never declares, but that one of its declared dependencies pulls in, whose installed version has published security advisories — and which the build installs for production, so it ends up in the shipped code. Almost all of a real submission's vulnerable packages are of this kind rather than named in package.json.

Before the review, the committed lock file is read in full: every package it records as installed, at any depth, declared or not. The packages that are declared were already audited on their own, so they are left out, and the rest are queried against the OSV vulnerability database in one batch. Only high and critical advisories are kept — a package nobody chose is worth the developer's attention when it fails the review, not when it merely appears in one — so every finding here is an error, and the advisory's own band is still named in the text. One kind of record is kept whatever its band: an advisory saying the package itself is malicious rather than vulnerable states no severity at all, and dropping it on that basis would discard exactly what this check exists to catch. Each finding anchors at the package's entry in the lock file. The check runs only for a source-code submission, since a shipped add-on carries no lock file.

When it fires The add-on is told that a package it does not declare, pulled in by one of its dependencies, has known security vulnerabilities, with the affected version, the advisory ids and the severity, and that this package ends up in the code it ships. It is asked to update the declared dependency that pulls it in — which usually resolves it, because a newer release often already depends on a fixed version — and to re-bundle and resubmit. Where no update resolves it, moving to a different or simpler build chain is named as the alternative.
It stops the review This check is one of the few that settle the submission on their own. When it reports at error severity, nothing further is put to a reviewer: the report drops every to-do item they would have been asked, keeps the code-review sections, and the developer’s text ends on the reason it is incomplete (“Known security vulnerabilities”). The case it exists for is a reviewer being asked to reproduce a build from a dependency tree the review has already rejected.
