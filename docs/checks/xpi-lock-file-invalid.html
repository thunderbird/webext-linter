Dependency the lock file does not pin error

xpi-lock-file-invalid

What it detects

A dependency declared in a shipped package.json as a version RANGE, which no lock file resolves. Such a declaration says a bundled file was copied from a published release, and the review checks that literally by fetching that release and comparing it against the shipped bytes. A range names no single release, so the lock committed beside it is what says which one was bundled.

Here the lock file IS committed and still records no version for this dependency - it came from another package file, records the package under another name, or does not parse at all. The submission is not asked to commit a lock it already has, so the remedy is to regenerate it, or to pin the dependency instead. Where no lock was committed at all the ask is the opposite one, made by xpi-lock-file-missing; a dependency is never reported by both. A source-code submission answers the same question against the tree the reviewer installs, so this check does not run there.

When it fires The developer is told the committed lock file records no version for the dependency, and is asked to regenerate it from this package.json, or to pin the dependency to a bare version instead.
