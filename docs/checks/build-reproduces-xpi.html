Reproducing the XPI from the source error

build-reproduces-xpi

What it asks

Under --llm-review, once the reviewer has held the build safe in the preparation, it asks them how the build came out: does it complete, from a clean copy with the dependencies installed exactly as the lock file pins them (npm ci, or pnpm install --frozen-lockfile), and does its result match the submitted XPI?

Reproducing the build is the reviewer's attestation that the shipped XPI comes from the source they read, which is what a source-code review rests on. The reviewer answers by comparing the build output the review links, where the agent built the add-on, or their own build, with the submitted XPI. It runs only where the reviewer decided the build is safe (when: build-judged AND build-safe): a build held unsafe is reported by build-unsafe and never built, and where nobody decided, a plain report included, build-review asks the whole build question.

Decision flow

flowchart TD
  A["The build, from a clean copy"] --> Q{"Does it complete, and does
its result match the submitted XPI?"}
  Q -- "Builds and reproduces" --> OK([cleared: the review goes on])
  Q -- "Does not reproduce" --> NR([ERROR: build-not-reproduced])
  Q -- "Does not build" --> BF([ERROR: build-fails])

It aborts the review It is asked ALONE, in the built phase, right after the Build Review Details and before the sweeps - ask batches, and nobody may be asked to install an XPI in the same breath as being asked whether the source builds into it. Its three answers are Builds and reproduces, which clears it, and Does not reproduce and Does not build, which clear it and report build-not-reproduced or build-fails, so the developer is told why, and the review is aborted late. It is asked under --llm-skip-manual too. A source whose preparation gave its rescue up ends the review through its vulnerability findings.
