Invalid lock file error

sca-lock-file-invalid

What it detects

A committed lock file that cannot install what the package.json declares. Reviewers reproduce the build with the package manager's strict install, which compares the two files before installing anything and refuses outright when they disagree.

Four things make a lock file unusable, and all four are reported here: it cannot be read at all, it can be read but is not a lock file this comparison recognises, it resolves nothing for a package the package.json declares, or the version it pins for one is not a version that package.json allows. The first two are worded apart because a developer would check which it is: one will not open, the other opens perfectly well and simply is not a lock. Production, build and optional dependencies are all checked, because the reviewer installs all of them. A dependency pointing at git, a URL, a file or a workspace is left alone: whether such a source is allowed is a separate question.

The last case is asked exactly as the installer asks it, and the two installers do not ask the same thing. npm resolves one version per package and checks it against the declared range, so replacing a range with the exact version already installed is not a fault - the lock still installs something the declaration allows. Comparing the two ranges instead would reject that, and would also miss the reverse: two ranges can overlap while the version actually pinned satisfies neither. pnpm compares the specifier it recorded to the declared one as text and refuses on any difference, which is what --frozen-lockfile does, so there the recorded string is the subject. The oldest npm lock format restates no ranges at all, so there only presence can be checked and no mismatch is ever claimed.

A finding is shown against the file its failing value is in: the lock, at the entry holding the version it pins, when the pin is what fails; package.json, at the declaration, when the lock resolves nothing for it - there being no entry in the lock to point at is the fault itself.

When it fires The add-on is told its lock file fails to pin the version used for one or more declared packages, which of them is unresolved or recorded differently, and that it should run the install again and commit the regenerated lock file. The report then closes, saying it is incomplete because the build cannot be reproduced.
It stops the review This check is one of the few that settle the submission on their own. When it reports, nothing further is put to a reviewer: the report drops every to-do item they would have been asked, keeps the code-review sections, and the developer’s text ends on the reason it is incomplete (“A build that cannot be reproduced”). Every question that remains would depend on installing and building the add-on, which cannot succeed, so the work it would otherwise put to a reviewer cannot change the outcome.
