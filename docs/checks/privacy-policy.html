Remote data transmission needs a privacy policy hold-or-error

privacy-policy

What it detects

An add-on that transmits data to a hardcoded remote server. When this happens, the listing must carry a privacy policy that discloses what is collected — but that policy lives in the listing field on the add-on site, not in the package, so it cannot be verified automatically. The trigger is deterministic, but the outcome is escalated to a human reviewer rather than reported as a finding.

The check looks only at the developer's own JavaScript, and only at overt transmissions. A destination the add-on assembles while it runs may be built from the developer's own constants or from something the user typed, and telling those apart needs the code read rather than scanned — so it is reported like any other site and MARKED, rather than dropped. A case a reader can dismiss costs a moment; a site nobody is shown is a blind spot nothing closes. A destination with nothing literal about it at all is left to the data-exfiltration review (which asks about consent), and a covert disguised channel is already a hard error in the disguised-* checks.

This is the disclosure angle, and it escalates one case per transmission site, each naming its host or carrying a hint where there is no host to name. The report still reads one line per host: repeats of one host are folded onto the first, which says how many others it stands for (collapse: subject in the registry entry) — unless a reviewer wrote about one of them, whose own words keep their line. Every site remains its own item, so each carries its own verdict.

When it fires A reviewer is asked to confirm the listing carries a privacy policy that details which user data is sent and to which services. The developer guidance explains that the policy must be the actual text pasted into the add-on site field — not a link to a remotely hosted policy — and that it must describe how the extension collects, uses, stores, shares or discloses information about people.
