Unsupported dependency source error

unsupported-dependency

What it detects

A dependency declared in package.json from a source the review cannot identify or verify. Only two sources can be vetted: an npm package and a GitHub URL, which is gated by popularity. Everything else is rejected. Whether the release a spec names can be pinned at all is a separate question, answered by other checks.

Before the review begins, the vendor resolver reads the package.json dependencies once and classifies each by its source. A local file reference, a link or workspace reference, a tarball URL, or a git source that is not GitHub cannot be resolved to a known upstream, so it is set aside as unsupported. This check reads that set and turns each entry into a finding, anchored at its declaration line.

Build dependencies count too, in a source-code submission. They are never shipped, but the reviewer installs them to reproduce the build, so a build tool pulled from an arbitrary git or tarball URL is code that runs on the reviewer's machine from a source nobody can check - if anything, a worse position than a bundled library, which is only read. In a built XPI the same entry is inert: nothing is installed there and build dependencies declare no bundled files, so it is left alone.

When it fires The add-on is told the dependency is declared from a source the review cannot identify or verify, and that only npm packages and GitHub sources are supported. The two submission types are told slightly different things. An add-on submitted as a built XPI is asked to re-declare it as a pinned npm package or a GitHub source, or to bundle the library as authored code so it can be reviewed directly - pinning is part of that answer because a shipped declaration must name one release. A source submission is asked only to re-declare the source, with the note that this applies to build dependencies too, since the reviewer installs and runs them, and that a library it bundles can instead be included non-minified in the archive.
