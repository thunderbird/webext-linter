testing-information

What it detects

This is a human-review item with no automated logic behind it. A reviewer asks whether the review can proceed with what the submission carries, or whether something is missing that only the developer can supply: credentials for a service the add-on signs in to, a test account, or instructions for reaching a feature. A developer must supply testing credentials where the add-on relies on a service.

It follows Test the add-on, because that is where the need shows itself - a reviewer finds out an add-on signs in to a service by trying to use it. This response asks for credentials and nothing else, so what a reviewer observes while testing is reported by that check rather than this one.

When it fires The developer is asked for detailed instructions on how to test the add-on, and, if authentication is required, for a test username and password supplied through the reviewer-only Whiteboard field. The review is, on its own, put on hold rather than rejected: nothing is wrong with the add-on, and a person continues once the information arrives. Alongside a real error the submission is rejected anyway, and the hold becomes one more item on that list.

Source of truth: the manual-checks entry in assets/registry.yaml.
