Vulnerable indirect build dependency error

vendor-vulnerable-indirect-dev

What it detects

A package the add-on never declares, but that one of its declared build dependencies pulls in, whose installed version has published security advisories. It is never shipped, but this check runs only for a source-code submission, where the reviewer builds the add-on from source — so it runs on the reviewer's own machine during the build.

Before the review, the committed lock file is read in full: every package it records as installed, at any depth, declared or not. The packages that are declared were already audited on their own, so they are left out, and the rest are queried against the OSV vulnerability database in one batch. Whether a package is build-time only comes from the lock file itself — npm's own dev markers, or, for a pnpm lock that has none, whether the package is reachable from the project's production dependencies. Only high and critical advisories are kept, so every finding here is an error, and the advisory's own band is still named in the text. One kind of record is kept whatever its band: an advisory saying the package itself is malicious rather than vulnerable states no severity at all, and dropping it on that basis would discard exactly what this check exists to catch. Each finding anchors at the package's entry in the lock file.

When it fires The add-on is told that a package it does not declare, pulled in by one of its build dependencies, has known security vulnerabilities, with the affected version, the advisory ids and the severity, and that although it is not shipped, reviewers build the add-on from source so it runs on the reviewer's machine during the build. It is asked to update the declared build dependency that pulls it in — which usually resolves it, because a newer release often already depends on a fixed version. Where no update resolves it, moving to a different or simpler build chain is named as the alternative.
