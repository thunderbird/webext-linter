Unknown or unsupported WebExtension API error

unknown-api

What it detects

Calls to WebExtension APIs (browser.*, messenger.*, chrome.*) that Thunderbird's annotated schema does not provide: an unknown namespace, an unknown member of a known namespace, or a member that exists but is explicitly marked unsupported.

Only the plain WebExtension code is checked — Experiment and privileged code legitimately use Thunderbird internals rather than the WebExtension schema, and dead code never runs, so both are excluded.

A namespace that the add-on's own Experiments define (the base namespace of any experiment_apis entry, for example calendar) is treated as known: the developer owns that API, so the whole namespace and everything under it is accepted rather than tracing each sub-API.

Every such reference escalates; this check never rejects on its own. That the name is absent is a fact, but whether the add-on is broken by it is not: a feature detection, a cross-browser shim, a cached capability flag or a try/catch fallback may carry the add-on where the name is missing, and deciding from the AST which of those covers a given call is a judgement whose wrong answer rejects a working add-on. So the check locates the question and a reader settles it against the schema, reading the site.

EVERY reference is listed, never one per name. Coping is a property of the site — one reference may sit in a try/catch with a fallback while the next is bare — so collapsing them would let a clear granted at the site someone read cover the sites nobody did.

When it fires Each reference is put to a reader under Extended Code Review, who reports it unless they can point at the guard. Where they do, the add-on is told the named API is not supported in the targeted Thunderbird version, with a link to the WebExtension API documentation.

Source of truth: src/checks/rules/unknown-api.js and its entry in assets/registry.yaml.
