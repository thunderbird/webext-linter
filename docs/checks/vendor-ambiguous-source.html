Ambiguous vendored source error

vendor-ambiguous-source

What it detects

A declaration whose source cannot verify the files paired with it. Two shapes reach this check: a single source URL declared as the origin of more than one bundled file — a file source verifies one file against the bytes at that URL, so pairing it with several is ambiguous — and a directory declared against a source that is not an archive of the upstream release.

A directory is verified by fetching the release as one archive and matching every file under the directory against its contents, so the source has to name that archive. Two do: a pinned npm package, resolved to its registry tarball, and a GitHub /tree/ URL, resolved to the repository ZIP. The URL of a single file does not — and neither does a CDN's directory listing, which is a web page. That case is settled before anything is fetched, precisely because such a URL usually is fetchable: it answers 200 with an HTML page, so the request succeeds and only the unpacking fails, which would otherwise leave every file under the directory unverified.

The fix is to give each bundled file its own distinct source URL, or — if the files come from one release — to declare the containing directory against a source naming that release. The vendor resolver pulls these declarations out of the VENDOR file (it does not attempt to verify them, and does not request them) and this check turns each into an error.

When it fires The add-on is told that the listed source URLs cannot verify the files declared against them — a file source verifies exactly one file, and a directory needs a source that can be fetched as an archive of the whole release. It is asked to give each file its own source URL, or to declare the containing directory against a pinned npm package or a GitHub tree URL.

Source of truth: src/checks/rules/vendor-ambiguous-source.js and its entry in assets/registry.yaml.
