The built XPI is fully included in the source archive warning

sca-xpi-fully-included-in-archive

What it detects

A source-code submission whose archive holds the built XPI entire: every file the XPI ships is byte-identical to a file the archive carries, wherever that file sits. A source archive is the readable source a build turns into the shipped package, not a copy of that package.

This does not re-route the review. A source archive is always reviewed as one, and this finding changes nothing about the review it appears in. Routing on it would be a bypass: a committed, unminified dist/ in the archive is its own twin under any content test, so a build could be dressed up as source and shrink its own review. At warning severity --warnings-as-errors can still refuse a submission at intake, while an update that got its packaging wrong is simply told what to change.

Two submissions look like this, and the check cannot tell them apart — which is why the response gives a remedy for each rather than assuming one. Either nothing was built, the shipped bytes ARE the submitted source, and the XPI on its own is a complete review target. Or a build ran and its output was committed beside the real source, in which case the archive is right to exist and the build output is what does not belong in it.

The comparison is content anywhere in the archive rather than name for name, so a build that merely relocates files is still recognized for leaving every shipped byte readable. Bytes are compared exactly, with no line-ending normalization: a file a build rewrote line endings in is a file the build touched. The finding names no file, since every shipped file is its subject, so the entry carries no location line.

Nothing about the build enters into it. A submission can be rejected for a build that cannot be reproduced — a missing package.json, an unusable lock — and still be told its archive holds the whole XPI: the two answer different questions, and a rejection printed beside this takes nothing back.

When it fires The archive already holds every byte the XPI ships. The developer is asked to submit just the XPI if it does not need to be built — source submissions take considerably longer to review — or, if it does, to remove the build output from the archive and submit only the source the build runs on. This review itself is unaffected: it is a full source review either way.

Source of truth: src/checks/rules/sca-xpi-fully-included-in-archive.js (which compares the two artifacts its input: both route carries) and its entry in assets/registry.yaml.
