The built XPI is fully included in the source archive error

sca-xpi-fully-included-in-archive

What it detects

A source-code submission whose archive holds the built XPI entire: every file the XPI ships is byte-identical to a file the archive carries, wherever that file sits. A source archive is the readable source a build turns into the shipped package, not a copy of that package.

This does not re-route the review. A source archive is never reviewed as the XPI it contains. Routing on it would be a bypass: a committed, unminified dist/ in the archive is its own twin under any content test, so a build could be dressed up as source and shrink its own review. It rejects the submission instead: an archive holding the built XPI could trick the build into handing back that copy rather than what it builds from the source.

Two submissions look like this, and the check cannot tell them apart — which is why the response gives a remedy for each rather than assuming one. Either nothing was built, the shipped bytes ARE the submitted source, and the XPI on its own is a complete review target. Or a build ran and its output was committed beside the real source, in which case the archive is right to exist and the build output is what does not belong in it.

The comparison is content anywhere in the archive rather than name for name, so a build that merely relocates files is still recognized for leaving every shipped byte readable. Bytes are compared exactly, with no line-ending normalization: a file a build rewrote line endings in is a file the build touched. The finding names no file, since every shipped file is its subject, so the entry carries no location line.

Nothing about the build enters into it. It runs right after the Experiment verdict and before the package.json and lock checks, so an archive that is a copy of the XPI with no build at all is rejected for holding the XPI, not for its missing package.json.

When it fires The archive already holds every byte the XPI ships. The developer is asked to submit just the XPI if it does not need to be built — source submissions take considerably longer to review — or, if it does, to remove the build output from the archive and submit only the source the build runs on.
It aborts the review This check is one of the few that settle the submission on their own. When it reports, no check after it runs and nothing further is put to a reviewer: the report drops every to-do item they would have been asked, and the developer’s text ends on the reason it is incomplete (“Source archive contains the built XPI”).

Source of truth: src/checks/rules/sca-xpi-fully-included-in-archive.js (which compares the two artifacts its input: all route carries, and is silent when a review has only one) and its entry in assets/registry.yaml.
