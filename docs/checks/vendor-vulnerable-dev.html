Vulnerable build dependency error

vendor-vulnerable-dev

What it detects

A build dependency the add-on declares whose installed version has published security advisories. Build dependencies are never shipped with the add-on, but this check runs only for a source-code submission, where the reviewer builds the add-on from source — so a vulnerable build tool runs on the reviewer's own machine.

Before the review, the committed lock file is read in full - package.json is not read for dependencies - and every package it records as installed is queried against the OSV vulnerability database in one batch. This check takes the ones the lock marks as declared by one of the submission's own package files and installs for the build only (an npm lockfile v1 records no declared set, so every package in one counts as declared). Only high and critical advisories are kept, and an advisory saying the package itself is malicious counts as critical, so every finding here is an error, and the advisory's own band is still named in the text. Each finding anchors at the package's entry in the lock file.

When it fires The add-on is told a build dependency has known security vulnerabilities, with the affected version, the advisory ids, and the severity, and that although it is not shipped, reviewers build the add-on from source so it runs on the reviewer's machine during the build. It is asked to update the dependency to a fixed release and resubmit.
It aborts the review This check is one of the few that settle the submission on their own. When it reports at error severity, nothing further is put to a reviewer: the report drops every to-do item they would have been asked, keeps the code-review sections of a printed report (an aborted --llm-review hands over no to-do item at all), and the developer’s text ends on the reason it is incomplete (“Known security vulnerabilities”). The case it exists for is a reviewer being asked to reproduce a build from a dependency tree the review has already rejected.
