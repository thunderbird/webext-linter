Lock file entries that install another release error

lockfile-injection

What it detects

A source-code submission whose committed lock file names one release of a package and installs another: an entry recording "version": "1.2.2" while its resolved URL (pnpm's resolution.tarball) fetches the 1.2.1 tarball, or another package entirely. The dependency audit asks about the name and version the entry records, while npm ci and pnpm install --frozen-lockfile fetch the URL, so the audit would vouch for a release the build never installs.

Every registry entry of the lock is compared, whatever its version looks like. A URL on the registry's tarball path (<package>/-/<name>-<version>.tgz) names its release, so it is compared offline. Any other URL on the registry is asked of the registry itself, once: where it serves that release's tarball is cached for good (--cache-npm-registry-dir), and a release it does not have counts as installing another. An entry with no URL is the registry's own tarball for its name and version, and a package bundled inside another fetches nothing of its own. A URL off the registry and GitHub is lock-foreign-source's.

It is the second check of a source review, so a forged lock stops the review before anything reads the lock to audit it. The preparation of a source code review (--llm-sca-review) asks the same question first, and does not audit or rescue such a lock.

When it fires The add-on is told which lock entries record one release but install another, and to regenerate the lock file with its package manager and commit it as the package manager writes it.
It aborts the review It settles the submission on its own (“Lock file entries that install another release”): what the audit would read is not what the build installs, so no audit of the lock could be trusted, and no check after it runs.
