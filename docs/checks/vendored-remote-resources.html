Remote load inside an upstream release manual-review

vendored-remote-resources

What it detects

A remote load — a script, style, frame or media reference — sitting inside a bundled file whose content matches, byte for byte, a published file of a known upstream release. The line is that release's own, so it is not something the developer wrote and not theirs to defend.

That does not settle it. Matching upstream is a fact about content, not about intent: it does not follow that the add-on needs this file, or that no build of the library avoids the remote load. So every such site is put to a person.

It turns on the content match, never on a declaration. A file declared as vendored but not verified is reviewed as the developer's own code, and its remote loads stay Remote resources findings — which is the whole point: a declaration must never buy an exemption on its own.

Both checks read one shared scan, so the add-on is walked once. Two limits are worth knowing: only the shipped XPI carries verified vendor results, so a source-code archive review never reaches this lane, and a vendored .js is dropped from the scan entirely — this applies to HTML and CSS references.

When it fires The reviewer is shown each site with the release it was matched against, and decides whether shipping that release as published is acceptable. Nothing is said to the developer unless the reviewer concludes it is not, in which case the entry's suggested response asks for a build of the library that loads nothing remotely, or for the dependency to be removed.

Source of truth: src/checks/rules/vendored-remote-resources.js and its entry in assets/registry.yaml. The shared scan lives in src/lib/remote-refs.js.
