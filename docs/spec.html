webext-linter specification

The specification of webext-linter's review: every path a run takes, every building block the paths are made of, and the decisions behind them. It is meant to be complete enough to rebuild the code from.

A run is one start of the linter. main (section 1) reads the command line and dispatches the run. An entry point (section 2) makes the first run of a review. Where an agent takes part, that run ends with a prompt, and the agent's next run, --llm-handback, comes back through the hand-back (section 3), which finds the review's state in one record, .review/state.json. The paths are drawn from the subroutines of section 4. Section 5 says what the agent is handed: the work folder, the prompts, the phases of the review loop, the sweep and the details blocks. Every run ends in exit handling (section 6), and section 7 follows each path through all its hand-backs. A box in a graph that is defined elsewhere links to its definition, so the flow can be clicked through.

The review itself is "populate ctx", which builds everything the checks read, and two runs of one function, runChecks, on it: first the early-exit checks, which can reject the add-on outright, then every other check. No check runs twice. The review then goes to "report the review" (plain), "start the review loop" (LLM) or, for an LLM review the early-exit checks rejected, "close the review".

The colours in the graphs:

  • the one extraction of the .xpi;
  • the early-exit checks;
  • "exit handling", which ends every run, with its exit code;
  • "continue after hand-back": the mode and step the next run continues in;
  • A, C and D: a subroutine drawn open where it is used (see "The graphs" under Decisions).

1 · main

main (src/cli.js) is the one function every run starts in. verify.js calls it with the arguments after node verify.js and exits with the code it returns. It reads the registry, judges the command line and hands the run to one of the three entry points (section 2) or to the hand-back (section 3), all inside the one catch (section 6.3), and every run ends in exit handling (section 6). main creates nothing itself: what a run creates, its entry point or the hand-back creates. A command line it refuses is a bad command line: "print the message" prints what is wrong, and exit handling exits 2 with nothing created.

1.2 · Before the command line is judged

  • The registry comes first. main reads and asserts the registry (loadRegistry) before it parses anything. It is the tool's own file, the same on every run, and nothing can be answered while it is broken, not even --help or a usage error, which print the check ids it names. A registry that cannot be read is a failure, answered by the one catch.
  • The parse. parseArgs takes the arguments against OPTIONS, strict, with positionals allowed. A command line it cannot parse (an unknown option, a string option with no value) is a bad command line: the parser's message, without node's hint about positionals starting with -, a blank line, and the help text. The banner is printed before it.
  • The output is routed before any guard, so every guard's message prints the same way:
    • the format is --report-format, or text. In json the run is quiet: no feed and no warnings, so stdout carries only the document. Messages through writeToStderr still go out.
    • --verbose switches on the debug lines, and progress lines show only in text. In a run that prints a prompt, a debug line goes with the held stderr messages (below), never onto stdout, so none lands in the prompt.
    • A run that prints a prompt (--llm-review, --llm-handback, --llm-auto-review) has the feed off, so no Setup or Activity section prints into the prompt, and holds its stderr messages back: exitWith writes them at exit as one block under ── Tool messages ──, since the agent's harness merges both streams and a message printed in place would read as part of the prompt. A bad command line in such a run is printed there too.
    • Colour only where the format is text and stdout is a terminal.
  • The run banner (runBanner): a blank line, > <name>@<version> review and > node verify.js <the arguments> from package.json, and a blank line, as npm prints its own run header. It goes through the feed's info, so a json run prints none, and it is left out where npm already printed its header (npm_lifecycle_script names verify.js, as under npm run verify). Every run that parses prints it before any branch, so --help and every refusal carry it.
  • --help is answered before any guard: a reader asking what the flags are is told, rather than refused over a flag the run never reaches. The help text goes to stdout, and the run exits 0. Only an unreadable registry and a command line that does not parse come first.

1.4 · The dispatch

  • --llm-auto-review: main reads the submission folder with scaSubmission (src/addon/submission.js), names only, top level only: exactly one .xpi, at most one other archive (named .zip, .gz, .tgz, .tar, .xz, .bz2, .zst, .7z or .rar, read from the end of the name), and no link among them. Anything else in the folder is ignored. With no source archive the run goes to reviewXpi (①a/②a) with --llm-review set and the format text, as --llm-review of that .xpi would. With one it goes to autoReview (③, section 2.3).
  • --llm-handback: runHandback with the work folder (section 3). It reads nothing else of the command line: the flags the review runs with come from the record.
  • Otherwise one add-on: reviewWithSource (①b/②b) where --sca-extracted is given, else reviewXpi (①a/②a), each with the format. Plain or LLM (--llm-review) is a mode of each, not a function of its own.

1.5 · The flags a review carries on

  • What the record holds (forwardedFlags): every flag OPTIONS declares and the run was given, named without its dashes, minus NOT_FORWARDED. Those are --llm-auto-review, --llm-review and --llm-handback, which run or carry on a review rather than describe one, --cache-clear and --report-format, which are the run's own, and the three --sca-* flags, whose folders the record names itself. Every entry point adds them to the record right after the load (addGiven). A folder among them is already the real, absolute folder, so it means the same wherever the review is started, and a record never names a folder for a later run to delete.
  • What a later run takes from it (recordedValues, for the review the unpack case, the build check's done case and the restart start): only the flags OPTIONS declares and NOT_FORWARDED leaves, each of its declared type, a boolean as true or false (false left out) and a string as a string. Then --llm-review is set, and the three value checks are asked. A record without a submission, or with a flag of the wrong type or a value the checks refuse, is a failure (recordError): the agent cannot repair it. The review and downgrade cases read only --warnings-as-errors, as the band policy every later pass reads under (bandPolicyOf).

1.6 · How main ends a run

  • The one catch is around the registry and the whole run, the hand-back included (section 6.3, answerError): a HandbackRefused is a refusal, anything else a failure.
  • Exit handling (section 6.2, exitHandling) is given the run's outcome: a bare exit code keeps the files, and with it whether the run issued a hand-back prompt, a bad command line is exit 2 with the files not kept (it claimed nothing, so nothing is removed), and the catch gives its own. A release that cannot remove what the run created prints Could not remove what this run created (<code>). on stderr and keeps the exit code.
  • verify.js ends the process, always through exitWith: the held-back stderr block is written, both streams are flushed, and the process exits with the code. What escapes main altogether (a rejected main, an uncaught exception, an unhandled rejection) goes to crash: its stack on stderr, what the run claimed released, exit 2.

2 · The entry points

What each entry point's own function does, up to where its run ends. After every run of checks the path calls one of the review functions (section 4): "report the review", which prints the report, "start the review loop", which starts the review and advances it to its first phase, or, for an LLM review the early-exit checks rejected, "close the review", which issues the closing prompt or the restart prompt. The path's other ends issue their own hand-back prompt (unpack, analyze, a build check step). Every run then ends in a green "exit handling", with its exit code, and where the agent carries on a red "continue after hand-back" names the mode and step the next run continues in (section 3). After a review function the red circle is dotted: it follows only where the handler issued a hand-back prompt, and is left out where none can follow (a plain run, an .xpi review rejected, whose LLM review can only close). A building block that meets an add-on or a source it cannot take throws a failure: the run's one catch prints it, and exit handling removes the run's files and exits 2. Section 7 draws each path followed through all its hand-backs.

  • Three entry functions, one per graph in section 2: ①a/②a (an .xpi), ①b/②b (an .xpi with --sca-extracted), and ③ (--llm-auto-review of a submission folder). The "plain or LLM?" decision is a mode parameter, not a second function.
  • An entry function ends where its run ends: at its first green "exit handling", where the dotted frames end. The red "continue after hand-back" after it is drawn inside the same frame, and inside the same coloured box, so the two read together (2026-10-27). It is still no step of the run, but where the next one picks up. Everything after that is a case of the hand-back, handled once, the same way for every path.
  • An entry point only starts unpack or a build check: the record written and the first prompt printed. "build-check" is no subroutine: the hand-back moves a build check on.
  • Both source paths end the same way once the source is in sca/: settle the package root, populate ctx, the early-exit checks, and the build check started at analyze (or for ①b the normal checks). They differ only in the one step that puts the source into sca/, the linter's copy or the agent's extraction.

3 · The hand-back

One entry point for every later run (runHandback, handBack, accept), a switch on state.json's mode. A run populates ctx only where it runs checks: in the unpack case, for the early-exit checks, which need the source, and when the build check is done, for the normal checks. Whatever an earlier run decided, the hand-back reads from state.json, and rebuilds only ctx. An answer of the agent's that a case cannot take is refused, with nothing written: the case throws HandbackRefused, and the run's catch prints the refusal and keeps the files (a D box), so the agent redoes that pass. The build check has a third outcome: a missing answers file or a missing entry hands the step's question out again, exit 0 (3.2.1), and at rescue an output path the output check refuses counts as a failed rescue, not a refusal (3.2.6). At unpack, entries other than SCA_EXPERIMENTS are ignored (3.1.1).

3.1.1 · What the unpack step asks and accepts

  • Who starts it.   • What the prompt names. 3.2.2 · analyze

  • Who starts it. "review the loaded submission", in LLM mode with a source, once the early-exit checks passed: mode build-check at analyze, its body buildCheckBody of the settled roots, every other slot null.

3.2.3 · override-unsafe and decision

  • Why two steps. An unsafe verdict is first only overridden or not, so decision always asks about a build held safe, whatever the verdict was. An overridden build is recorded as today's override always was: buildSafety unsafe with buildSafe true. No field of its own records it.
  • override-unsafe asks. llm-sca-review-prompt.override-unsafe, naming ANSWERS and the Build Review Details block (as at decision, below).   • override-unsafe accepts and refuses.   • decision asks. llm-sca-review-prompt.decision, naming ANSWERS and the Build Review Details block (buildDetailLines: the submitted .xpi, the source folders, build.md, the verdict, build-issues.md and the lock's counts from the audit at analyze, as the review's own details blocks name them, followed by the llm-phases.waiting line for decision). 3.2.4 · The audit of the lock

  • Where it lives and when it runs. auditRoot in src/build-check/audit.js, asked of the roots at analyze, once a build-guard check is not switched off and before anyone is asked, and again of the rescued copy's roots at rescue. It decides nothing but whether the lock is clean or rescuable, and counts it. Every other reason to stop is the review's.
  • The order of its questions.
    • The load. The tree roots.used is loaded as the review loads the source archive (loadSourceArchive, then scaViews). One the loader refuses is not read in full.
    • Before any network. More than one committed lock (committedLocks), then a lock entry installed from a source the audit does not read (lockSourceGaps). Either makes the lock not read in full.
    • lockfile-injection's question. An entry that installs another release than it names (findLockInjections), asked offline for a URL on the registry's tarball path and of the npm registry for one off it. One found makes the lock not read in full, and OSV is asked nothing.
    • Popularity, the blocklist, then OSV. resolveVendor with reviewerInstalls, then verifyScaDependencies. It first asks each declared package's popularity, by npm downloads or, for a GitHub install, the repository's stars. A declared package that is not a confirmed widely-used library is recorded as unpopular, and makes the audit unreviewable. It then audits with the policy blocklist read from the shipped assets/library-blocks.yaml: every package the lock installs is matched against the blocklist first, a banned release is recorded as blocked and never asked of OSV, and the rest are asked of OSV's batch endpoint. Only high and critical hits are put into the four lists (vulnerabilities, devVulnerabilities, treeVulnerabilities, treeDevVulnerabilities, by declared or pulled in, shipped or build-only), a malicious package counted as critical. A package whose worst advisory is moderate is kept apart, only to be counted. A chunk OSV does not answer ends the run as a failure, never as an incomplete audit.
    • Complete. The audit read the tree in full where a governing lock exists and parses as a lock the readers know (governingLock, unreadableLock).
  • The vulnerability counts. vulnerabilityCounts: moderate is the number of moderate packages, high and critical the hits of each severity over the four lists. A blocked release is in none of the lists and is not counted.

3.2.5 · build

  • What it asks. llm-sca-review-prompt.build, naming ANSWERS, SCA_PACKAGE_ROOT, LLM_BUILD_ROOT (the package root's place in build/, buildRootOf), SCA_BUILD_REPORT. 3.2.6 · rescue

  • What it asks. llm-sca-review-prompt.rescue, naming ANSWERS, RESCUE_ROOT (the package root in rescued/), LLM_BUILD_ROOT, SCA_BUILD_REPORT and the two commands that make build/ a fresh copy of the whole rescued/ (rm -rf and cp -a, quoted for the shell). The agent changes only the copy's package.json and lock with lock-only commands, audits until no high or critical advisory remains, and builds only in build/, never in rescued/. The entries are those of build, with LLM_BUILD_OUTPUT from llm-sca-review-prompt.rescue-output and its own failed label.
  • What it accepts and refuses. The entry's shape as at build, with the same refusals for a missing, doubled or null entry, an entry it did not ask about, and an output that is no label and no path. The path itself is not refused: one that outputAt would refuse counts as a failed rescue (producedIn).
  • The linter's own audit. Whatever the agent answered, the rescued copy's roots are audited again. rescuedVulnerabilities is their counts where that audit read the tree in full, and null otherwise.
  • Outcomes.
    • A path inside build/, a clean copy, and a build that reproduces the XPI (the linter's comparison, xpiMatch, says match): done, with buildResult built, the output and buildMatch match recorded, and the roots left in rescued/, so the review reads the copy.     • A path inside build/ and a clean copy, but no match: the vulnerable code may ship, so the rescue does not count. The record is written at done with buildResult rescue-mismatch, as a failed rescue is below: output and match null, the roots mapped back into sca/, then build/ deleted, rescued/ left as it is. The original is reviewed, its vulnerability checks abort the review, and the review's unbuildable fact holds.
    • Otherwise (the failed label, a path the output check refuses, or a copy not clean): the rescue failed. The record is written at done with buildResult rescue-failed, output and match null (nothing is compared), and the roots mapped back into sca/. Only then is build/ deleted (removeBuild). rescued/ stays as the agent left it: a folder of the submission the review does not read. The original is reviewed unrescued, and its vulnerability checks abort the review. The review's unbuildable fact holds.

3.3.1 · Accepting a pass

  • accept takes a pass back (src/report/loop.js), called by the review case (reviewCase, src/cli.js), which hands the accepted record and its settled review to "advance the review". It works on a copy of the record and writes nothing, so a refusal leaves every file as it was.
  • The steps, in order:
    • It finds the phase the record is at (state.phase) among llm-phases.phases.
    • It reads the answers file's entries (readHandback).
    • It works out what went out again: it settles the review with the verdicts so far and renders the same entries through the same function (askedIn), against the run facts that pass read. Nothing of what was handed out is read back from the file.
    • It checks what came back against what went out (answersOf, src/report/handback.js), each entry by its index.
    • A words phase: each answer that is no choice's label is held to the note's rule (checkedNote).
    • A hints phase: it reads every sweep answers file this review named, all before anything is recorded (sweptResults).
    • It adds the phase to issued, then records the pass: a hints pass routes the sweep's results into the review as cases of their checks and clears the pre-sweep (routeSweep), a value pass records its value (recordValue), a verdict or words pass records each answer under its ref, and a case sent on with ask is stamped instead (recordVerdicts).
    • It settles the review with the verdicts so far and the new answers. That settle is the pass's one settle (4.15).

4 · The subroutines

Every building block the paths are drawn with, one subsection each: its graph, what it takes and returns, and the decisions behind it. Where one calls another, the call is a box of its own in its graph, drawn open in the paths (section 2). "print the message" and "exit handling", which end every run, are in section 6.

  • The rule for a building block (2026-10-27): a common subroutine does only what is the same at every use, and returns a value. What differs between callers is never decided inside it: each caller decides it on that value. So "load the .xpi" returns the loaded add-on, and "settle the review" the settled review with its abort reasons, which the caller counts as plain or as the loop counts them. A block that would have to decide something only some callers need is no common block. The same holds for errors, and every function behaves alike: an error is always thrown, never returned, and whether to handle it, or a certain type of it, is each caller's own decision. What ends the run alike for every caller (a failure, or in a hand-back a refusal) no caller catches: it reaches the one catch in main ("load the .xpi" on an add-on it cannot read, a step on an answer it cannot take). A caller that decides an error differently catches only its own type and handles it, and everything else passes untouched to main: "approve the sca folders" throws ScaFoldersRejected (what is wrong, and with which folder), which ①b/②b catch and print as a bad command line, and the unpack case catches and throws on as a refusal. A result is no error and is returned: the abort reasons of "settle the review", an early-exit run that did not pass, a rejected review.

4.5 · "populate ctx"

"populate ctx" makes everything a review's checks read, before any of them runs. It is called once per run that runs checks: by "review the loaded submission", and by the build-check case once the build check is done. It reads the add-on in xpi/ and, in a source review, the source in the tree the review reads, both where they are. It works out what the shipped add-on declares, the review schema and, for an Experiment, the Experiment verdict, and builds the contexts each check is routed to. The review data behind those contexts is not computed here: each piece is computed the first time a check asks for it.

4.5.1 · What it takes, returns and promises

  • It takes the work folder, the sca folders where the review is a source review (settled in sca/, or the rescued copy where the build check chose it), and the flags it reads: the band policy (--warnings-as-errors), --allow-experiments (read by the Experiment verdict alone), the cache folders and the CDN lookup switch. From the record it takes the Experiment verdict where an earlier run decided it, and the build check's results where the build check is done.
  • It returns ctx: the registry under the run's band policy, the shipped manifest, the Experiment verdict, the source archive where there is one, the schema with the stamps the report prints for it (source, branch, channel), the review's meta, the mode and the sibling contexts.
  • It claims nothing and writes nothing into the work folder. What it fetches lands in the caches outside the work folder: the schema and the Experiment allow-list. The run's own cache in the work folder (.cache/osv.json, .cache/popularity.json) is written only by the review data, so only once a check asks for it.
  • It reads none of the options only the review needs: what an agent is asked (--llm-review, --llm-skip-summary, --llm-skip-sweep), the check lists (--checks-only, --checks-skip), --eslint, and downgradedFrom.
  • The mode follows from one fact and is assigned nowhere: a source review exactly where it is handed the sca folders (kind sca), an .xpi review otherwise. What the .xpi looks like never changes it, and neither does the Experiment verdict: a rejected Experiment is reviewed in the mode it was given, and its first early-exit check stops it.
  • It fails by throwing a failure, which the run's one catch handles (section 6): a schema it can neither fetch nor find complete in the cache, a cache known to be stale that cannot be refreshed, a schema file that does not parse, and an Experiment whose bundled files need the allow-list when the allow-list cannot be fetched (no verdict is guessed without it).

4.5.4 · The review data

  • Behind async getters on the context: ctx.vendor(), ctx.bundled(), ctx.jsSources(), ctx.apiUsages(), ctx.buildReview() and ctx.lockInstalls(). vendor is the review target's alone, buildReview and lockInstalls the source's alone, and a getter asked of an artifact it does not serve throws. The all context has none: its checks ask ctx.xpi or ctx.sca.
  • Computed once per artifact, on the first ask, and every later ask answered from the same result. A review computes what its checks read and nothing more: a check that does not run costs nothing.
  • Only final data is handed out. The stages run in a fixed order (below), and a getter resolves every stage that writes its answer before it answers, so a stage that revises an earlier one (the CDN identification, the audits) is done first.
  • A network question with no answer is a failure: the getter that asks a host that does not answer (OSV, the CDN, the registry, a library source) throws a failure, which the run's one catch handles (section 6), since an unanswered question would otherwise read as "nothing found".
  • Each source is parsed once, and the syntax tree is dropped after the parse has stored what the checks read. What checks derive from that (the API resolution, the permission analysis and the like) is built from the stored results on the first read and never parses again.
  • A check is a pure reader. It never parses, never fetches and never changes the artifact, so two checks asking the same question always agree.
  • The network: OSV and the popularity hosts are asked through the run's cache in the work folder, so a source review asks again little of what its build check asked. Pinned library sources come through the shared sources cache.
  • The feed: each stage prints its line in the Activity section, under the check that first needed it.

4.5.6 · What a parse stores

  • Each source is parsed once, and every extraction runs on that one parse. The small results are stored on the source, and the syntax tree is dropped, so memory holds one tree at a time.
  • The load graph: the local imports, the loader calls the schema knows, the first ES-module statement, and for an Experiment the files it injects. A source the parser cannot walk is recorded with the reason and the line.
  • The API grounding: the WebExtension API usage, and the Web and DOM API calls that need a permission.
  • The content: remote code, network sinks, unsafe HTML, privileged core symbols, synchronous XMLHttpRequests, debugger statements, async runtime message listeners, and the code atoms without comments.
  • Every source is extracted in full, authored or not. Whether a non-authored file's hits reach the report is each consumer's decision: every content scan skips the non-authored set. A permission is used, and a file is loaded, whoever wrote the code.

4.5.7 · The classification

  • Each JS and CSS file is classified once per artifact from the bytes it ships: library where its SHA-256 is a release in the known-library hash list (identified as name and version), minified by its statement density, obfuscated where it matches a known obfuscator. The files the vendor reading verified are vendored.
  • The non-authored set is every vendored, library, minified or obfuscated file. Every content scan skips it.
  • The CDN identification asks jsDelivr, by the file's SHA-256, about a file the hash list did not know: a minified one, or a readable one large enough to be a library. A hit on a popular package joins the libraries. A hit on a package that is not popular counts only where the package name matches the file's name, and is then identified but untrusted: a minified or obfuscated one stays non-authored, a readable one is reviewed as authored code. Any other hit is discarded, as if the lookup had missed. Before it, vendor entries that could not be fetched are reconciled into the untrusted family. So this step both adds to and removes from the non-authored set, which is why the parse is ordered after it.
  • Hits are cached on disk, since a file hash names one release for good. A miss is never cached, so it is asked again on the next run. With the lookup off, every file keeps its first classification.
  • Experiment code is the add-on's privileged code, and each artifact finds it its own way. In the .xpi it is traced: every file the WebExtension entry points of the shipped manifest.json reach is WebExtension code, and every other file counts as Experiment code (pureWebExtensionReachable, src/lib/reachability.js). In the source it is the Experiment folder, named by --sca-experiments or the agent's unpack answer and shown as SCA_EXPERIMENTS. The checks of WebExtension code leave it out, the dynamic-code checks (eval-call, string-timer, remote-eval, function-constructor) read only code outside the WebExtension code, and nothing judges what the Experiment does with its privileges: experiment-manual-review asks the reviewer to read its code in the .xpi.

4.5.8 · The derived caches

  • What several checks derive from the stored results is built on the first read and kept on the context's cache: the API resolution, the permission analysis, the outbound sinks, the eval scan, the remote references, the locale messages and the localized names. The reachability graph is kept per context as well, outside the context itself.
  • A derived cache never parses: it reads only what the parse stored. A cache nobody reads is never built.

4.5.10 · The feed

  • The feed shows what a run is doing. Only ①a and ①b print it, and only with a text report. No other run prints a feed.
  • It has two sections: Setup, printed by "populate ctx", and Activity, printed by runChecks ("run the checks", "The feed: Activity"). Both functions run on every path, but print only in ①a and ①b.
  • Setup opens with ── Setup ── and a blank line and prints one numbered line, [i/total], per step that runs and has a line. The total is sized by asking the same conditions the steps run under. A step prints the one line it declares and no other. The lines, in order:
    • Reading add-on: the read of xpi/. It is made before the heading, since it says whether the add-on declares Experiments, which sizes the total.
    • the schema, named as it is resolved: Fetching review schemas (<branch>), Fetching review schemas (all channels) where the cache is incomplete, or Refreshing review schemas (cache older than a day);
    • Verifying bundled experiments, for an Experiment only.
    The source read prints no numbered line. Where the package root moved below the folder named, it prints one detail line, Package root: sca/<to> (sca/<from> holds no package.json), so the reviewer sees which folder the verdicts are about. A blank line closes the section before Activity opens.
  • One line from outside both: the network layer prints Waiting <n>s: <host> is refusing requests where a fetch has to wait, in whichever section is open.
  • Not feed: the run banner, which main prints in every text run before any entry point, and the report's header, which "report the review" prints with the report.

4.5.11 · Decisions

  • "populate ctx" is the one place that hard-codes how review data is made: xpi/ and sca/ read in place, the manifest, the schema, the Experiment classification, and the contexts and lazy review data every check reads. It claims nothing, writes nothing into the work folder, and reads none of the review-only options. Everything else is registry-driven.
  • The Experiment classification is data in ctx, as the schema is. experiment-not-allowed reports it in the early-exit checks, and experiment-modified in the normal ones. Which groups are rejected stays marked by experimentVerdict, the one reader of --allow-experiments, since no check reads a run option.
  • ctx is populated once per run that runs checks, at the point that run reaches them: after the load and source in one-run paths, in the unpack case, and in the hand-back that finds the build check done. By then the source read may be the rescued copy, and the build decided.

4.6 · "run the checks"

runChecks runs the checks of one review against the contexts "populate ctx" built. A path calls it at most twice, with one boolean selector, early-exit: true runs only the checks marked review-early-exit, false every check but those. Both calls read the same ctx, and no check runs twice. Whether the early-exit run passed, none of its checks reporting an error, is its caller's to read.

4.6.1 · What it takes, returns and promises

  • It takes the registry, the selection (the check lists --checks-only and --checks-skip, --eslint, and the facts a check's condition reads), the early-exit selector, the count so far where an earlier run of the path handed one over, and the sibling contexts.
  • It returns every finding, stamped with its check's id and band, every to-do the checks escalated, the checks that ran in order, and the count.
  • It writes nothing. It only prints the Activity section of the feed. What a check asks of the review data is computed then, through the getters ("populate ctx", "The review data").
  • It fails by throwing a failure, which the run's one catch handles (section 6): a registry entry whose module is missing or exports no run, a check that throws, and a check that breaks its contract (below). A review missing a check is never published.

4.6.4 · Escalating what the code cannot settle

  • A check that cannot settle a case does not guess: it escalates it, with the file and line to look at, and the case becomes a to-do.
  • Its section follows from the check, never from the case. A check that writes its question for an agent lands under Extended Code Review, where an agent can answer it by reading the add-on. One that writes it only for a person lands under Extended Manual Review: what only the listing, the build or a person's judgement can settle. Every case a check raises asks the same question, so a check that needs two questions is two checks.
  • Every to-do carries its check's suggested response: the text the developer receives once the case is settled against the add-on.
  • An escalation carries a locus like a finding, minted by whatever holds the file.

4.6.5 · Which checks abort the review

  • A check aborts the review by naming a reason, under one of two keys of its registry entry. Some findings settle the submission on their own, and the review is then aborted rather than carried on, above all before anyone is asked to install or test the add-on.
  • review-late-exit: <reason> is the default. Its error stops nothing while the review runs. Every check runs, and the loop still builds, spawns, verifies and settles, so verify can withdraw a wrong finding first and the developer is told everything in one round. The loop counts a late reason once the phase that would go out is ask or the close (runOf), and a plain report counts it at its end.
  • review-early-exit: <reason> is for the two cases where the rest of the review is no use: a submission refused whatever its code says, and a forged lock every later reading would take at its word. Its error ends the early-exit run at once (abortsReview): no check after it runs, and nothing it would have asked for is computed.

4.6.6 · What the registry enforces on the abort keys

  • Not both: an entry names review-early-exit or review-late-exit, never both.
  • Severity: an aborting check is error or auto. A hold-or-error band is decided against the rest of the review and would make the abort depend on when it is asked.
  • A defined reason: the reason names an id of review-early-exit.reasons, and every id there is named by some check, so no reason is unreachable wording (assertReasonDefined).
  • No sweep on an early-exit check: a sweep's hints are merged unverified and an early abort verifies nothing. A late-exit check may sweep, since it is judged after the sweeps and verify.
  • Early before late: every early-exit entry comes before the first late-exit entry in registry order, so no late finding is counted unverified by an early abort.
  • Only a check that runs may carry either key (the registry schema's only-a-check-that-runs): a manual-checks entry cannot.
  • A process value's reports names an error check with an early or late reason, whose input reads one artifact.
  • The source markers review-downgrade and review-unbuildable sit only on a check that aborts, and only on input: sca or all (assertSourceMarker).
  • Early-exit checks are left in by the check lists: --checks-only and --checks-skip cannot drop them (checkSelected).

4.6.7 · The markers beside the abort keys

  • review-unbuildable: true says no build can be made from the source by the review's own rules: no usable package.json, no single readable lock to install from, a lock entry installed from a source the audit cannot read, or a declared dependency nobody can review. It is on sca-package-file-missing, sca-package-file-invalid, sca-lock-file-missing, sca-lock-file-invalid, sca-lock-file-multiple, lock-foreign-source and unpopular-source-dependency, and each of them carries llm-verification: false: the build check's audit stopped on the same fact and built nothing, which no verdict of the agent undoes. Where one of them aborts the review, or the build check's rescue failed, the run fact unbuildable holds (runOf), every built step reads NOT unbuildable, so built is skipped and nobody is asked to build. The review goes on to the sweeps and ends late.
  • build-guard: true marks a check an agent's build relies on: lockfile-injection, build-registry-redirect, lock-foreign-source and the four dependency-vulnerability checks. Where every one of them is left in by the check lists, the run is build-guarded (buildGuardIds, reviewBody and the build check's buildGuarded). Where one is switched off, nothing vouches for what an install pulls in: the build check does not let the agent build, and the review shows neither the built Build Review Details nor LLM_BUILD_RESULT. A build-guard check carries no when:, which the registry refuses, so whether the run is guarded follows from the selection alone.

4.6.10 · Decisions

  • The review is split in three: "populate ctx" and two runs of the checks. Both runs are one function, runChecks, given one boolean selector, early-exit: true runs only the checks marked review-early-exit, false every check but those. Neither run is a subroutine of its own (2026-10-28): each is that one call, drawn in place with its selector in parentheses, since a wrapper per value of a parameter adds nothing. Whether the early-exit run passed (one of them reports an error, or none does) is its caller's to read on the edge.
  • Early-exit checks always run. --checks-only and --checks-skip cannot name them, and a --checks-only list still runs them.
  • One run of the early-exit checks per path, once ctx holds every artifact they read (settled 2026-10-26). experiment-not-allowed reads the .xpi and lockfile-injection the source, so on a source path they run after the copy or the unpack, and before the build check. In ③ with a source the agent extracts the archive first: a rejected Experiment costs that one extraction, which keeps the early-exit checks a single block on every path.
  • A passed run of the early-exit checks leaves nothing behind. It holds because early-exit checks are severity: error, escalate nothing and have no when:. The registry asserts all three.
  • No check runs twice. The normal run's selector leaves the early-exit checks out. What is computed again in the second run of a path that checks the build is ctx: readableXpi and the lazy review data.
  • The gain of lockfile-injection running before the build check is that a forged lock does not go through the analyze and decision turns. Nothing is built from a forged lock in any case: the build check's audit refuses it.

4.8 · The record

  • One record, .review/state.json, with a mode (decided 2026-10-26):
    • The modes: unpack is ③'s one step of getting the source, build-check is the build check from analyze on with its roots, and review is the review loop.
    • A step moves the record on with one atomic write (writeFileAtomic, a write and a rename). A crash leaves it in the old mode or in the new one, never both, so no hand-back deletes a record and no rule ranks left-over files.
    • The hand-back dispatches on the mode, not on which files exist.
    • A review start that fails is retried: the record is still in mode build-check, at done, so the next hand-back starts the review again.
    • The build check's results are permanent (everything of it the review and the checks read, the build decision, the build result and the vulnerability counts among them): the build check adds them to the record when it is done, and the review reads them there.
    • Sealed and read-only as a whole: only the linter writes it.
    • One reader checks the shape for the record's mode. A folder holding prepare.json is refused with exit 2: it cannot be carried on.
  • The record has a permanent part, only ever added to, and a current part, the one a mode change replaces (2026-10-28). "load the .xpi" creates the work folder and in it an empty .review/state.json. From then on:

At the loop's end it holds mode review's body without mode: that review as the loop holds it, the verdicts so far (answers, values) and what the close reads of the loop (run, issued, products, paths, roots, vulnerabilities). It holds no rendered report.
      • the build check, when it is done: the build check's results, everything of it the review and the checks read (the build decision, the build result and the vulnerability counts among them), added before the review starts. A review start that fails is retried from done and finds them there.
    • The submission's folders are permanent facts, named by the record, never inferred (2026-10-28). Which folders the submission is made of is not guessed from the kind, the mode or the roots: each folder is a fact of its own, for example folders: { xpi, sca, rescued }, added once by the step that creates it, so adding one never replaces another:
      • xpi/: the entry point, with what was given, right after "load the .xpi" (every path, the restart included);
      • sca/: ①b/②b's entry point right after "copy the source", and ③'s unpack case once "approve the sca folders" has taken the agent's sca/;
      • rescued/: the build check, right after it creates the rescued copy, in the hand-back that audits the lock and finds it rescuable, on the way into rescue.
      The hand-back's folder check reads this set and nothing else. Which tree the review reads, sca/ or rescued/, is the build check's own decision and part of its results: it decides what the review reads, not which folders are checked. Folders the agent works in, such as build/, are not the submission's and are not named.
    • The hot runs' switch is read where it is used, never recorded (2026-10-28). WEBEXT_LINTER_AGENT_BUILDS=1 lets the hot runs (tests/hot/) skip the build check's decision question.     • The current part is the mode, its step or phase and its own body. "start a mode" replaces only it, and "the record at the next step" and "the record at the close" move only it on. None of them deals with the permanent part, so no step "keeps" anything and no step can drop a fact by accident.
    • Who comes first does not matter: every writer writes into the record the load created, and no subroutine takes "the record, or none in a first run".
    • A record with no mode (an empty one, or a plain run's, which never gets one) holds no review in progress: the hand-back's entry fails it, see below.

There it checks the registry's rule for the restart: a source review rejected only by checks a review of the .xpi alone cures, every aborting check carrying review-downgrade: true (a review of the .xpi alone cures the finding), and its .xpi reviewable on its own (xpi-reviewable, a fact the first run records). Does it hold, it issues the restart prompt instead of the closing prompt: it starts mode downgrade ("start a mode", with no body: the review and its verdicts are in the permanent part already), writes review.md and issues the question. Does it not, it puts the record at the close (the current part set to closed) and issues the closing prompt, so every later hand-back is refused ("this review is finished"), in a first run as in the loop, into the record the load created. A finished review fails the rule, since nothing aborted it, so the one check covers every end.
    • The hand-back's downgrade case reads the reviewer's answer to the restart prompt, its one decision: "xpi" loads the .xpi into a new work folder and calls "review the loaded submission" with LLM, the recorded flags and downgradedFrom, and this review's folder stays as it is. "keep" settles the review again from the permanent part and issues the closing prompt with the rejection report, leaving out the summary and the details the restart prompt already showed. The close is simple on purpose: "issue the closing prompt" always takes a settled review and writes review.md from it, for every close alike, and stores no rendered report to reuse. We know that after the restart prompt this is a rewrite with the same content: nothing changes the inputs in mode downgrade, so the settle gives the very report already written. It is done anyway because it keeps the code simple and robust: the close needs no "already written, skip" case and knows nothing of the downgrade, the record holds only inputs, never output, and review.md, which the agent can write to, is never read back as a source. Any other answer is refused. The review case does not ask "restart as an XPI review?": it accepts the pass and calls "advance the review".
    • "keep" does not pass through it: the hand-back's downgrade case issues the closing prompt itself ("issue the closing prompt"), so the restart is offered once. A review rejected by its early-exit checks, such as one lockfile-injection rejects, is offered the restart as a later rejection is.
    • Why: checked where the loop would close, the question is decided once and answered once.

5.3.4 · The condition language

  • The grammar (src/checks/condition.js): expr := term (OR term)*, term := factor (AND factor)*, factor := NOT factor | "(" expr ")" | name | call, call := "value" "(" name "," name ")". NOT binds tightest, then AND, then OR.
  • Names and operators: a name is a lower-case word of letters, digits and hyphens, not opening with a hyphen. The operators are upper case, so an upper- or mixed-case word that is no operator is refused. Spaces, tabs and newlines separate tokens.
  • One function, value(phase, id), with exactly two names. It holds once the named phase returned that id, read from the review's recorded process values. Any other call is refused.
  • Parsed once, at load (parseCondition, in loadedStep and loadedPhase), and evaluated by holds over the fact set and the values. The parser names what it expected and the 1-based position where it stopped.

5.3.5 · Process values

  • A phase answering value asks for one: an answer that steers the review and settles no item. It comes back as one of the offered labels, and recordValue stores the value's id under the phase's name in the review's values, never in answers.
  • Any value clears the to-dos routed there: every open to-do in the phase is recorded as cleared.
  • reports: a value that names a check adds that check's finding, with the check's severity and the artifact its input reads (xpi, or sca, or for source the review's own), stamped llm-verification: false where its check says so, and gives the review new refs (assignRefs). The check aborts the review, so the finding aborts it the way any finding of that check does.
  • asked-in: a check whose question is put in a phase of its own names that phase. The phase is then routed, relays the to-do's message as its question and is issued only while the to-do is open.
  • The restart prompt's value is read under the name downgrade (DOWNGRADE_PHASE). xpi (DOWNGRADE_RESTART) restarts the review as an XPI review. Any other offered value closes it, and the close is issued with that value among the review's values, so value(downgrade, keep) reads it there.

5.3.6 · What the registry loader enforces

  • The shape (assets/registry-schema.yaml, loop-phase-entry and llm-phases): name, intro (may be empty), answer (one of ANSWER_KINDS: hints, verdict, words, value, end), verbs (may be empty) and steps are required. ends-turn, verb-prose, question and values are optional. preamble, frame, handover, prose-style, reading-rule, waiting, refused, build-results (closed over WORDED_BUILD_FACTS), restart and phases are required.
  • The linter's texts carry their placeholder: frame {{review}}, handover {{command}}, refused {{problem}} (PHASE_TEXTS, assertPhases, src/checks/registry.js:1749).
  • The restart prompt answers value and has a question (registry.js:1762).
  • Exactly one phase answers end, and it is the last (registry.js:1786), and its steps carry {{details}} and {{tally}} (FINAL_SLOTS, registry.js:1795).
  • No name twice among the phases and the restart prompt (registry.js:1806).
  • Verbs: only a verdict phase names verbs, and it names at least one (registry.js:1812). Each is one of LOOP_VERBS: reported, cleared, withdrawn, ask. Each verb has a verb-prose entry and each verb-prose entry is a verb the phase accepts (registry.js:1847).
  • A turn-ending phase shows {{details}} or {{buildDetails}} in some step (registry.js:1833) and has a waiting.next entry.
  • The waiting line: waiting.text carries {{next}} and no {{count}}. next.ask carries {{count}} and no other entry does. Every next entry is decision or a turn-ending phase (registry.js:1866 to 1909).
  • Every step and preamble part (assertStep, registry.js:1499) is a mapping with a non-empty text, does not number itself, and carries no key but text and when.
  • Every condition (assertCondition, registry.js:1536) parses, names only facts of its prompt (REVIEW_PROMPT_FACTS in the loop, SCA_PROMPT_FACTS in the build check), and every value(phase, id) names a phase answering value (the restart prompt among them) that offers that id.

5.3.8 · What the phase order must guarantee

  • The close is last. Enforced by the loader.
  • verify and settle come before ask. A late exit halts the run once ask would go out, so a phase after ask never runs in a review a late finding aborts, and verify could not withdraw that finding. Not enforced.
  • A question asked alone comes before ask (built today), or the halt at ask withholds it. Not enforced.
  • spawn comes before verify and settle, so the sweep's cases join their first pass. The walk would still reach them after, with a second pass of each. Not enforced, and not needed for correctness.
  • The loader checks no other order, and does not check that verify, settle, ask or spawn exist, though the code routes items to the first three by name. An item routed to a missing phase is open in no issued phase, and the walk passes it by to the close.

5.4 · The sweep

  • The agents the review starts (the spawn phase): a sweep agent per tree with a sweep to run, which sweeps that tree and returns hints for the checks, and the report agent, which writes the summary report of the add-on for the reviewer (summary.md, left out under --llm-skip-summary). The build report (build.md) is no sub-agent's: the agent itself writes it in the build check's analyze step. No spawn step waits for its agent, so all of them start at once, and the phase's last step waits for every sweep agent before the pass is handed back. The summary report is not waited for: it is not needed until the reviewer is handed the review details.
  • A sweep covers a check's blind spot. Some checks scan for a set of forms that cannot be finished, so the check declares the class of code it cannot see as an instruction for a reader. What the reader finds belongs to that check. The instruction is the registry's text and is carried through unchanged.
  • The keys follow the route. A check on a single-artifact route (xpi, sca, source) authors sweep-instruction, and the tree is the one its input reads. A check on input: all, which names no single artifact, authors sweep-instruction-for-xpi, sweep-instruction-for-sca or both, and each one it authors is a sweep of its own with its own words and its own tree. The two forms are never mixed (assertSweepInstruction, src/checks/registry.js).
  • The registry refuses at load
    • a per-artifact key on a single-artifact route, and a flat sweep-instruction on input: all,
    • an instruction that is not a non-empty string,
    • a sweep on a check whose severity gives a reported case no band: auto and none are refused, a concrete band and hold-or-error are taken,
    • a sweep on a check whose response (or per-mode response) holds a {{placeholder}}, since a swept case brings no item to fill it,
    • a sweep on a check marked llm-verification: false, since only verify audits a swept hint (assertLlmVerification),
    • a sweep on a check that names a review-early-exit reason (assertEarlyExit, see "Which checks abort the review").
  • The checks that declare one, in registry order, all in deterministic-phase:

5.4.1 · The list and its labels

  • The list is made once, by the review's checks (preSweepOf, src/pipeline.js, called from reviewOf). It walks Registry.sweepInstructions(mode), one entry per instruction in registry order, and keeps an entry only where its check ran in this review, so --checks-only and --checks-skip carry through. It fills in the artifact of a single-artifact route from the context the check ran on (ctxForRule), and drops an entry whose tree this review does not have, such as the source half of cleartext-transmission in an .xpi review. An empty list is stored as null.
  • Each entry carries its check id, its artifact, the check's title, its band (suggestedVerdict), the instruction, the check's response for this review's mode, and its label.
  • The label is a number, unique across the whole review: the entry's place in the list, from 1. It is not counted per tree, so the two answers files never both hold a label 1 and an answer is never read against the wrong request. The plain report numbers its Standard Code Review list by the same labels, so a reviewer covering a blind spot by hand and an agent sweeping it see the same list under the same numbers. Nothing else of the review (a check id, an artifact) reaches the sweep agent.
  • A review the early-exit checks rejected has no list: only the early-exit checks ran, and none of them may author a sweep.

5.4.2 · The request

  • One sweep agent per tree. The list is grouped by artifact, and each tree gets one request that holds every sweep of that tree, so one reader walks the tree once for all of them and the two trees stay independent (sweepRequests, src/report/sweep-files.js).
  • The requests are made when mode review starts (reviewBody, src/report/loop.js), since each request carries its tree's path, which no later pass could rebuild. Each tree's request text and answers path are stored in the record under paths.sweeps, keyed by artifact, and each tree with a request sets the run fact sweep-xpi or sweep-sca (sweepRun). Nothing is written to disk.
  • Where it is printed: inline, in the spawn phase, as the slot {{sweepXpi}} or {{sweepSca}} of that tree's step, with the answers path as {{sweepXpiAnswers}} or {{sweepScaAnswers}} (sweepSlots). The step wording is llm-phases.phases[spawn], whose two sweep steps hold on sweep-xpi AND NOT aborted and sweep-sca AND NOT aborted. The orchestrating agent relays the request unchanged and writes the sweep agent's reply unchanged to the answers file once it comes back. The phase's last step, on (sweep-xpi OR sweep-sca) AND NOT aborted, waits for every sweep agent before the pass is handed back.
  • The request's shape, paragraphs apart by a blank line, each prose paragraph on one line:
    1. the order to sweep this folder and read nothing outside it, and the tree's absolute path on a line of its own, indented,
    2. the reading rule (registry llm-phases.reading-rule),
    3. how many sweeps it holds, each its own request, answered from that folder alone,
    4. to judge by effect rather than by method, and to resolve values assembled at runtime,
    5. one paragraph per sweep: Label <n>: <title>, then the instruction with its whitespace collapsed,
    6. the reply's shape, {"answers": {"<label>": [...]}}, indented,
    7. that it lists every label, an empty list where nothing was found, with nothing around the JSON,
    8. what one entry holds (file the absolute path of a file in the folder, as the agent opened it, hint of at most MAX_HINT characters, 500, line where it sits on one) and a worked example laid over this request's own labels: the first shows resultShape of the folder (src/config.js), every other an empty list,
    9. the prose style (registry llm-phases.prose-style),
    10. that the agent writes no file.

5.4.3 · The answers file

  • One file per tree, .review/sweep-<artifact>.answers.json with the artifact in lower case: .review/sweep-xpi.answers.json and .review/sweep-sca.answers.json (workPaths(work).sweep). The orchestrating agent writes it, from the sweep agent's reply. The linter writes none of it.
  • Its format is JSON, one document {"answers": {"<label>": [entries]}}. JSON has one quoting rule, where YAML would break on a hint such as http://host: thing.
  • Both names are claimed at the review start: claimedNames always lists both sweep files, whether or not this review sweeps, and a start that finds either already there is refused.
  • The files are read when the spawn pass is accepted (accept, src/report/loop.js, for the phase whose answer is hints), before anything is recorded, and all trees in one read (sweptResults). A file that cannot be acted on refuses the whole pass, so no tree's hints are half applied. The spawn phase's own answers file lists no entry, and an entry handed back there is refused like any entry not asked about.
  • Refused (readSweepAnswers, then checkedResult, src/report/sweep.js), each refusal naming the one thing to fix:
    • a file that cannot be read, or is not JSON, or holds no answers object,
    • a label the request did not ask about,
    • a label left out or answered null: an empty list is "swept and clean", a missing one cannot be told from a sweep nobody ran,
    • a label answered with anything but a list,
    • an entry that is not an object, or carries a field other than file, line and hint,
    • a file that is missing or empty, not an absolute path, or holds a .. segment,
    • a file that is not a regular file inside the swept tree, resolved through links: outside the tree, the tree itself, a folder, or a link out of it. One inside is recorded relative to the tree, which is matched as given and by its real path, so a source in a wrapper folder is recorded with that folder,
    • a line that is not a whole number from 1, or past the file's last line,
    • a hint that is not a non-empty string, or is longer than MAX_HINT.
  • The label is resolved by the linter. Each result is given the check and the artifact of the sweep the label was asked for, read off the stored list, never off the file.

5.4.4 · Where a hint lands

  • A sweep is a detector and nothing more. A hint is a location its check's own detectors missed, and from then on the case is one of that check's, handled as a case the check found for itself (mergeSweepResults, src/report/sweep.js):
    the owning checka swept case becomes
    escalates (sectionFor names a section)An escalation of that check, in that section, worded from that check's own instructions (manualEscalations, renderManualItems), marked extended.
    does not escalateA finding of that check, at the check's band (suggestedVerdict), with the locus and the hint, worded later by renderFindings. Verify audits it like any other finding.
  • The hint is a locus annotation: it names what sits at that line. What the developer reads is the registry's response.
  • Deduplication is on check, artifact, file and line: against the other results of the same reply, against the to-do list and against the findings. A location already covered for that check in that tree is dropped, and the same relative path in the other tree is a case of its own.
  • A result for a check that authors no sweep throws: it can only mean the registry changed under a review in flight.
  • After the merge the new cases are given refs of their own (assignRefs, continuing their check's count), so they are open and verify asks about them, and the stored list (preSweep) is cleared. A sweep that found nothing clears it too, since it is over either way. Only a review that asked no tree (--llm-skip-sweep, sweep null) keeps it, for the reviewer to sweep by hand. Each routed case is listed for the audit line, as <check> [<artifact>] (<file>:<line>) → <section> or → finding.

5.4.5 · Leaving it out, and the Standard Code Review list

  • --llm-skip-sweep withholds every request (llmSkipSweep): no paths.sweeps, no sweep-<artifact> fact, so no step that starts a sweep agent prints, and no answers file is read. It is refused on the command line without --llm-review or --llm-auto-review. It is not one of the skips a when: names (PROMPT_SKIPS).
  • The Standard Code Review list (preSweepSection, src/report/format.js) is the plain text report's section for the stored list, printed whether or not anything was found. Each item is laid out as <label>) <title>: <instruction>, then Sweep: <tree path>, then the suggested verdict and the suggested response a find would carry. It sits after Extended Manual Review and before Standard Manual Review, and the Summary counts its items as "standard code review item(s)". An aborted plain report keeps it, since reading code is safe. The JSON report drops it.
  • An LLM review prints no report, so its sweeps are handed out only as requests, and its closing tally counts no standard code review item.

6 · How a run ends

Every run ends in a green "exit handling", one place in the code. It prints nothing: what a run produced, the path printed before it (the report, a prompt, the closing prompt), and an error is printed by the one catch of the run: a refusal as the refused text, a failure as its message and "verify failed". Both go through one writer, "print the message", boxed in green (D) with the exit handling that follows it. Exit handling is given two values and acts on them, without deciding anything:

  • whether the files this run wrote stay: they stay when the run did its job, a refusal included, so the agent can redo the pass in the same folder. After a failure the files and folders this run created are removed (releaseClaims, src/util/claims.js), and anything the run found there is left alone.
  • the exit code, written on each green circle: 0 after a hand-back prompt, whatever the review's errors: the unpack and analyze prompts, every step's and phase's prompt, the first prompt and the downgrade question. 0 or 1 after a run of checks that prints a plain report or issues the close, by whether the review has errors. 0 or 1 at a close reached in a loop pass or after "keep", by the review's errors. 2 after a refusal or a failure.

A red "continue after hand-back" follows where the agent carries on. It is not an action of this run, but where the next one picks up: the mode, and the step or phase within it, that state.json now holds and that the hand-back's switch reads (section 3). After a refusal the record is unchanged, so the next run continues in the same mode and step.

6.1 · "print the message"

  • One writer prints the message a run ends with, boxed in green (D) with its exit handling (2026-10-28): "print the message", given the stream and the text, drawn with them in parentheses.     • a bad command line: stderr, what is wrong with the flag, without "verify failed", since nothing was verified, then exit 2 with nothing created.
